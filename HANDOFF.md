## 4. App rendering logic

### Four tabs (redesigned Aug 2026 into a time/task-management app)
The old single **☀️ Digest** tab was split into three, plus the unchanged Recaps tab:
- **✅ To-Do** — the primary tab. The task-management surface (MIT + Eisenhower + 5-min rule + Power Hour). Loads the latest `digest-YYYY-MM-DD.json`.
- **📅 Meetings** (labeled "Mtgs") — the meetings section, split out. Carries a Power-Hour reminder that meetings live in the afternoon.
- **🏢 Clients** — client status cards, split out and sorted by severity.
- **📝 Recaps** — unchanged; loads `recaps-YYYY-MM-DD.json`, editable email drafts with "Open in Outlook".

All three digest tabs render from **one** fetch. `loadDigest()` stores the JSON in `digestData` and renders all three containers (`#content`, `#meetings`, `#clients`) up front; `switchView()` just toggles visibility (no refetch). Recaps still lazy-loads on first view.

### To-Do tab — the task-management model
Built on four Kevin Kruse concepts. All task rows are checkable `.ai[data-id]` rows, so the existing state/done-file pipeline is unchanged.

- **Power Hour banner** (top) — reminds Nick mornings are for deep work; block set by the `POWER_HOUR` display constant (`8:00–11:00 AM`). Meetings tab shows the afternoon counterpart.
- **MIT (Most Important Task)** — one task elevated into an accented banner. Chosen by `pickMIT()`: explicit `mit:true` flag → else first `critical` → else first Eisenhower "do" task → else first task.
- **Quick Wins (5-minute rule)** — tasks with `durationMin <= 5` (or `quick:true`) are pulled into a "do these now" strip, ahead of the matrix. The 5-min rule wins over quadrant placement.
- **Eisenhower matrix** — remaining tasks placed by `classify()` into a 2×2 grid (CSS grid, stacks to one column under 560px): Do First (urgent+important), Schedule (important, not urgent), Delegate (urgent, not important), Eliminate (neither). Classification reads explicit `importance`/`urgency`; if absent it infers from `priority` (critical/high → urgent+important, normal → important+not-urgent).
- **Scheduling (Hybrid, suggest + one-tap)** — "Do First" and "Schedule" tasks show a `＋ Add to Outlook` button. It builds an Outlook web **calendar** compose deep-link (`outlook.office.com/calendar/0/deeplink/compose`) — no calendar permission needed; Nick reviews and saves. Times come from `slotStart`/`slotEnd` (ISO) if present, else `parseSlot()` best-effort parses `suggestedSlot` against the digest date. The parser handles "8:00–8:20 AM EDT" style; a slot that straddles AM→PM with two different meridiems can mis-parse the end time — Nick sees it in Outlook before saving, so it's non-blocking.

### Task sources / `collectTasks()`
The app treats emails and (going forward) Teams/tl;dv items as tasks, not separate sections. `collectTasks()` returns `sections.todos[]` directly when present; for legacy digests it folds `overdue/critical/today/tomorrow/emails` into one task list. There is no longer a standalone Emails or Teams section in the UI.

### Meetings tab
Meetings grouped by `day` with a day separator; `talkingPoints` (or legacy `context.agenda`) render as a bullet list. Reuses `renderMeetingsSection()`.

### Clients tab
Sorted critical → needs-attention → in-progress → on-track → waiting. Each card: colored dot, status badge, activity, current status, next step. Reuses `renderSection(..., 'client')`.

### Progress bar
Counts checkable task rows on the To-Do tab. Shown only on the To-Do tab (hidden on Meetings/Clients/Recaps).

**Two hard todo rules added to the live procedure (Aug 31 2026):**
1. **Carry forward every unfinished todo** (`SKILL-updated.md` Step 0, "Carry forward every UNFINISHED todo"). 2. **Assignment scope is a hard filter** (`### todos`, plus enforced at Step 1 email and Step 3 Teams): a todo must be work assigned to Nick. Anything he is merely **CC'd** on / included in / a team-wide FYI is dropped — *being on a thread is not an assignment*. When unsure, leave it out. Such mail may still update client state (Step 3c) without creating a task.

Note: the app's own filters never hide *unchecked* tasks (`completedEarlier` and the completed-log key set only ever contain items actually checked off), so disappearing open tasks are always a skill-side carry-forward problem.

## 5. Todo ID format

IDs are constructed as: **priority prefix + first 4 words of title, lowercased, spaces to hyphens.**

Prefixes:
- `crit-` for critical priority
- `tod-` for high (today) priority
- `tmrw-` for normal (tomorrow) priority

Example: "Honda (HTC) — Configure sFTP for production entries" → `crit-honda-htc-configure-sftp`

IDs must be stable across days for the done-file carry-forward to work. The prefix keeps items matched to the right priority band even if re-ordered.

## 6. The Claude skill — how digests are generated

**Skill path:** `morning-action-digest` in the Cowork plugin
**Runs:** scheduled task, 8:00 AM EDT daily

The skill:
1. Reads yesterday's done file to find completed item IDs to skip
2. Searches Outlook email (7 queries), calendar (today + 48h ahead + 2-day lookback), and Teams (5 queries) via the Microsoft Graph MCP connector
2b. **(Aug 2026) Scans Nick's own sent "Recap: ..." client emails since the last run (Step 1b) — a primary todo source.** Pulls the "Decisions and next steps" bullets assigned to Mely/Nick (prefixed "Mely:"/"Nick:"/"Me:"/"I:"/"Myself:", or unprefixed) and skips bullets assigned to the client. These get `source: "recap"` and the same priority/importance/urgency classification as any other todo — no auto-elevation. On overlap with another source, the recap-sourced item wins.
3. Verifies automated meeting note action items (tldv, no-reply senders) against Nick's outgoing email before flagging as overdue
4. Synthesizes everything into todos/meetings/clients
5. Saves two files to OneDrive:
   - `Daily json files/digest-YYYY-MM-DD.json` — powers the PWA app
   - `Daily json files/HTML Version/Morning Action Digest - WEEKDAY, MONTH DATE, YEAR.html` — standalone static version

**Senders excluded from digest:** wordpress@mely.ai, auto-notify@netchb.com, compliance@pmkintl.com, noreply@upcentral.app

**Subjects excluded:** anything starting with `EMP-`

**HTML Version:** A self-contained static file built from a template (`template.html` in the skill directory). Uses `localStorage` for checkbox state and has a "Save progress" button that downloads a done JSON file. Useful as a backup view or for sharing.

## 7. Known design decisions

- **`Daily json files/` is excluded from git.** Data stays in OneDrive only. The repo only tracks the app code. This means git history is clean and no client data ever hits GitHub.
- **Legacy JSON format support.** Pre-July 2026 digests used separate `today[]`/`tomorrow[]`/`critical[]` arrays. The app renders both formats to avoid breaking old files.
- **`talkingPoints` vs `context.agenda`.** Current skill generates `talkingPoints[]` directly on each meeting object. Older digests used `context.agenda[]` inside a `context` sub-object. Both are supported.
- **`window.location.origin` as MSAL redirect URI.** Dynamic — works on any host. Azure app registration must be updated any time the app moves to a new URL.
- **No service worker.** The manifest.json exists (makes it installable as a PWA) but there is no `sw.js`. No offline caching — the app always fetches live data from OneDrive.
- **Body text in todos is rendered unescaped.** The `body` and `detail` fields from JSON are injected directly as innerHTML. Safe as long as Claude is generating the content, but worth noting if the data source ever changes.
- **.git folder lives inside OneDrive.** This causes harmless `unable to unlink tmp_obj_*` warnings when committing (OneDrive tries to sync git internals). Commits still succeed. If this becomes a problem, move the repo outside OneDrive and use a symlink or just copy files manually before pushing.

### `Daily json files/digest-tasks.json` — manual To-Do edits (NOT in git)
Persists the user's hands-on edits, kept **separate** from `digest-state.json` (done state) so the checkbox pipeline is untouched. Keyed by dateKey:
```json
{ "2026-08-13": {
    "overrides": { "<taskId>": { "quadrant": "do|schedule|delegate|eliminate|quick", "mit": true, "order": 2, "deleted": true } },
    "manual":    [ { "id": "man-<base36>", "title": "...", "source": "manual", "quadrant": "...", "durationMin": 10, "dueDate": "..." } ]
```

### App behavior (index.html)
- `computeTodo(dateKey)` is the single source of truth for the To-Do tab: merges skill `todos[]` + `manual[]`, drops `deleted`, resolves the MIT (explicit `mit:true` wins, else `pickMIT`), buckets the rest by `effQuadrant` (override → 5-min quick → Eisenhower `classify`), and sorts each bucket by `order`.
- **Drag-and-drop:** pointer-based (touch + mouse), via the ⠿ handle. Drop targets are the four `.quad`s and the Quick Wins `.section` (all tagged `data-drop`). Dropping sets a quadrant override + reorders. `justDragged` suppresses the click-to-complete that can trail a drag.
- **Tap ⋯ menu:** move to any quadrant / Quick Win, set or clear MIT, delete (manual tasks are removed; skill tasks get `deleted:true` = "remove for today").
- **Reorder by number:** each task in a quadrant / Quick Wins shows an editable position `<input class="ord-num">`; typing a new number calls `reorderTo(id, bucket, pos)`, which rewrites `order` overrides for that bucket. (Replaced the old up/down menu items.)
- **＋ Add task:** inline form (title, details, quadrant, minutes, due date, Set-as-MIT) → appends to `manual[]`.
- Every edit calls `commitTasks()` → re-render (`rerenderTodo`) then `saveTasksState()` to OneDrive. `wireTodo()` re-attaches all handlers after each render.
- Manual tasks are normal `.ai[data-id]` rows, so completion still flows through the existing done-state + done-file pipeline.

### Suggested date + roll-forward (#1)
Scheduled tasks show date + time from `slotStart`/`slotEnd`. The skill emits a slot only when a task has a real `dueDate`, scheduled ≤2 business days before it (Step 3b). Because slots are generated in the morning for the morning Power Hour, `reflowSlots()` runs at render time: future slots stay put; **past slots are stacked forward from the next Power Hour opening** (today if still before 11 AM, else tomorrow 8 AM), in original order, tagged "· moved up". The chip label and the Outlook deep-link both use the reflowed time, so the app never suggests a time that has already passed. Power Hour bounds are `POWER_HOUR_START`/`POWER_HOUR_END`.

### Client card fields + editable owner (Aug 2026, later same session)
Client card now shows: name + health badge, meta line, **Status** ← `state` (short workflow label, e.g. "Ramping up", falls back to `currentStatus`), **Latest activity** ← `activity` (narrative — brought back after being briefly removed), **Next step** ← `nextStep`, **Owner** (an editable `<select>` of `Nicolas Ferron` / `Edward Ko`), **Contacts**, footer (`@domain`, `lastMeeting` link).

The Owner selector writes **directly to `clients.json`** via Graph (`setClientOwner` → `saveClientRegistry`): it finds the client by name/shortName/aliases (or appends a new entry) and sets `owner`, then re-renders. Because `clients.json` is the skill's ownership source, changing an owner to Edward drops that client from Nick's digest on the next run. Skill emits `state` + `activity` (replacing the single `currentStatus`) and must **always look up `lastMeeting` in tl;dv** — the earlier gap where some cards lacked a last-meeting link was a skill completeness issue, now required.

### Completed tasks are retired permanently (completion memory)
**Root cause found (Aug 2026):** the skill gives the same task a different ID almost every day (LLM-derived from wording), so exact-ID retirement never matched — completed tasks kept coming back. Fix is a **cumulative completion log** matched by title, not ID:
- App writes `Done/completed-log.json` = `{ items: [{ id, title, key, date }] }` on every checkbox (`logComplete`; `key = normSig(title)` = lowercased alphanumeric). Rows carry `data-title` so `toggle` can capture the title.
- `computeTodo` hides a task if: it's done today → keep (greyed); else `completedEarlier(id)` (same id, any prior day) → drop; else its `normSig(title)` is in `completedKeySet()` → drop. So a re-emitted duplicate is hidden even when its ID drifts, as long as the title is close.
- The **skill reads `completed-log.json` in Step 0** and drops any todo that *semantically* matches a completed item (handles rewording the app's exact-title match can't), and now builds **stable IDs** (`prefix-client-action`, reused across days). This is the durable fix — it stops re-creation at the source.
- `digest-state.json` per-day flags + `completedEarlier` remain as the id-based layer.

### Full-width 4-column board
